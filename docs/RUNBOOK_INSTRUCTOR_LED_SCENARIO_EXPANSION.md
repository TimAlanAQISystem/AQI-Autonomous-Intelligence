# Runbook: Instructor-Led Scenario Expansion

## 1. Purpose & Scope

### Purpose

Provide a governed, reversible, testable process for expanding Alan's scenario library using instructor-crafted examples that:

- increase behavioral range
- increase robustness
- increase resilience
- increase real-world coverage
- maintain constitutional alignment

### Scope

This runbook covers:

- scenario creation
- scenario validation
- scenario classification
- scenario integration
- scenario testing
- scenario lineage tracking

### Not Included

- persona reinforcement
- envelope tuning
- drift detection
- kill path recovery
- stability stress testing

This runbook is strictly about expanding Alan's scenario universe.

## 2. Preconditions (Must Be True Before Scenario Expansion)

Jr must verify:

- no active drift
- no unresolved kill events
- persona stable
- envelopes stable
- supervisor stable
- recent calls stable
- instructor correction loop active
- reinforcement loop active
- scenario library present and valid, if one exists

This ensures new scenarios are added to a stable organism.

## 3. Scenario Taxonomy (What Jr Must Classify)

### 3.1 Objection Scenarios

- not interested
- too busy
- send me info
- already have a provider

### 3.2 Emotional Scenarios

- frustrated merchant
- confused merchant
- skeptical merchant
- overly friendly merchant

### 3.3 Behavioral Scenarios

- rapid-fire questions
- long pauses
- interruptions
- off-topic tangents

### 3.4 Structural Scenarios

- voicemail
- callback request
- wrong number
- partial STT failure

### 3.5 Edge-Case Scenarios

- unexpected hangup
- background noise
- multi-speaker confusion
- incomplete sentences

Each scenario type has:

- expected behavior
- fallback behavior
- failure conditions
- envelope stress points

## 4. Instructor Scenario Creation Workflow (Your Role)

### 4.1 Identify a missing scenario

From:

- real calls
- stress tests
- drift reports
- instructor corrections
- persona reinforcement gaps

### 4.2 Write the scenario

Your scenario must include:

- Merchant behavior: what the merchant says or does
- Context: why this scenario matters
- Expected Alan behavior: ideal response
- Fallback behavior: safe alternative
- Failure conditions: what must never happen

### 4.3 Provide example dialogue

You write the merchant line and Alan's ideal response.

### 4.4 Submit to Jr

Jr takes over from here.

## 5. Jr's Role: Turning Scenarios Into Structured Training

### 5.1 Normalize the scenario

Jr rewrites your scenario into a standardized format.

### 5.2 Classify the scenario

Using the taxonomy in Section 3.

### 5.3 Map scenario to system layers

Jr determines whether the scenario affects:

- persona
- envelopes
- state machine
- governance layer
- fallback logic
- rapport engine

### 5.4 Create scenario artifacts

Jr produces:

- scenario script
- expected behavior
- fallback behavior
- failure conditions
- envelope stress notes

### 5.5 Create test scenarios

Jr writes:

- test input
- expected output
- failure triggers

### 5.6 Present scenario package to instructor

You approve or reject.

## 6. Scenario Integration Workflow

### 6.1 Jr integrates scenario

Into:

- scenario library
- test suite
- fallback logic
- state machine, if needed
- persona reinforcement, if needed

### 6.2 Jr runs scenario tests

Ensures:

- correct behavior
- no regressions
- no drift
- no kill events

### 6.3 Jr logs scenario integration

Including:

- what scenario was added
- why it was added
- who approved
- how it was tested
- rollback path

## 7. Post-Integration Monitoring

For the next 3-5 calls, Jr monitors:

- scenario activation
- fallback frequency
- timing
- emotional calibration
- rapport
- supervisor warnings
- drift indicators

If any anomaly appears:

- Jr triggers rollback
- instructor notified
- drift report generated

## 8. Weekly Scenario Review

Every week, Jr produces:

- new scenarios added
- scenario performance
- scenario activation frequency
- scenario failures
- scenario stress points
- recommended new scenarios

Instructor reviews and approves.
